## What The Prompt Tells You

```text
 󰀵 MacFeyz  …/Caristant.API  󰘬 main !3 ─────── 󰌛 net10.0  󰔛 1s ✔  󰅐 02:47

❯
```

Left to right: which operating system, which machine, where you are, which branch and how dirty it is. Then the connector line. Then, right-aligned: which runtime the current directory uses, how long the last command took, whether it succeeded, and the time.

| Segment | Shows | Appears |
|---|---|---|
| **Host** | OS icon, hostname, role icon | Always |
| **Path** | Working directory, truncated to the repo | Always |
| **Git** | Branch and status counters | Only inside a repository |
| **Right** | Runtime, `kubectl` context, duration, ✔/✘, clock | Runtime and context only when detected |

The **role icon** in the host segment is what makes this useful across the homelab: `` on a Proxmox host, `󱃾` on a Kubernetes node, `` inside a container. Detection is by filesystem, not by hostname — `/etc/pve`, `/var/lib/kubelet`, `/.dockerenv` — so a renamed machine still identifies itself correctly.

## What It Replaced, And Why

The setup before this was **Oh My Zsh + Powerlevel10k**, with a Gruvbox colour scheme in iTerm2.

Nothing was wrong with it. The reason for the change was Warp: its block model, its own autocomplete and its own history search make most of what a shell framework provides redundant. Keeping Oh My Zsh loaded to get `gst` and a completion system that zsh already ships felt like paying rent on an empty room.

What came out:

| Removed | Size | Replaced by |
|---|---|---|
| `~/.oh-my-zsh` incl. the p10k clone | ~17 MB | 60 lines of `~/.zshrc` |
| `~/.p10k.zsh` | 91 KB | `~/.config/starship.toml`, 5 KB |
| p10k instant-prompt cache, `gitstatus` | ~2 MB | not needed — starship is fast enough without |
| iTerm2 and its Gruvbox colour file | — | Warp |

What was kept, deliberately: **the p10k frame line.** The horizontal rule that connects the left prompt to the right one is the one thing from the old setup that was genuinely missed. In Starship that is the `fill` module.

### Why Starship

Three properties, in order of importance here:

1. **A single static binary.** This is the decisive one. The prompt has to run on `pve0` and on the nodes, not just on the Mac — and installing a zsh framework on a Proxmox host to get a nicer root prompt is not something anyone wants to maintain. Starship is one file in `/usr/local/bin` with no dependencies.
2. **Shell-agnostic.** bash on the servers, zsh on the Mac, one config file for both.
3. **Declarative.** A TOML file instead of a generated 91 KB shell script, which means it can be reviewed in a diff.

## The Part Everyone Gets Wrong: Where A Prompt Runs

A prompt is not a picture the terminal draws. It is **text generated by the shell process on the machine the shell lives on**.

When you `ssh root@pve0`, a shell starts *on pve0*. It generates a string, sends it down the connection, and your terminal paints it. Your Mac's Starship is not involved and does not know you are logged in anywhere.

Two consequences, and both are good news:

**Starship has to be installed on the host.** There is no way around it — see [servers](./servers). But it needs neither zsh nor a framework: `eval "$(starship init bash)"` in `~/.bashrc` is the whole integration, and bash is what root uses on Proxmox and Ubuntu anyway.

**Fonts do not have to be installed on the host.** The server only sends Unicode code points. The glyphs are rendered by *your* terminal, using the font on *your* machine. A bare Debian install with no fonts at all still shows the Proxmox icon correctly.

## How The Powerline Segments Are Built

Starship has no concept of a "segment". A segment is what you get when the foreground colour of a separator glyph matches the background colour of the block before it:

```text
[ content ](bg:A) [](fg:A bg:B) [ content ](bg:B)
                   └── the arrow: A-coloured triangle on a B background
```

The glyphs come from the Powerline block in the Nerd Font:

| Glyph | Code point | Role |
|---|---|---|
| `` | `U+E0B6` | Rounded cap, left end |
| `` | `U+E0B0` | Hard separator, pointing right |
| `` | `U+E0B2` | Hard separator, pointing left (right-hand side) |
| `` | `U+E0B4` | Rounded cap, right end |
| `─` | `U+2500` | The connector line (`fill` module) |

### Empty tabs instead of decorative arrows

The double separation between path and branch, and between runtime and clock, is a **real segment with no content** — an arrow into an intermediate colour, immediately followed by an arrow out of it:

```text
[ …/Caristant.API ](bg:#81a1c1) [](fg:#81a1c1 bg:#3f899f) [](fg:#3f899f bg:#88c0d0) [ 󰘬 main ](bg:#88c0d0)
                                 └────────── the empty tab: #3f899f ──────────┘
```

The first attempt at this drew a single arrow in a contrasting colour *on the same background*. It looked wrong, and the reason is worth writing down: when the arrow's tip and the surface behind it are the same colour, the eye reads a floating arrow rather than a boundary. A boundary needs a colour change on both sides of the glyph. Two arrows and one intermediate colour give exactly that.

The intermediate colours are derived per palette, not hard-coded, so switching schemes keeps the effect intact.

### Segments that are sometimes absent

This is where most Powerline configurations — including Starship's own `gruvbox-rainbow` preset — leave an artefact. If the separators sit in the top-level `format` string, they are static text: they render even when the module between them produces nothing. Outside a git repository you get a small coloured stub where the branch should be.

The fix used here is to move each separator **into the module it belongs to**:

- The arrow *into* the git segment lives in `git_branch.format`. No repository, no branch module, no arrow.
- The empty tab after a runtime lives in each runtime module's format. Not a Node project, nothing appears. Two runtimes detected, they get separated from each other too, which is the right behaviour anyway.
- The arrow *closing* the left group is the only case that needs help, because its colour depends on whether git is present. Two tiny custom modules handle it, one for each case.

Those two modules originally shelled out to `git rev-parse`, at 20 ms each. They now walk up the directory tree in pure shell looking for `.git`, which costs 4 ms:

```sh
d=$PWD; while [ -n "$d" ]; do [ -e "$d/.git" ] && exit 0; d=${d%/*}; done; exit 1
```

`-e` rather than `-d` on purpose — in a git worktree, `.git` is a file.

## Why The Config Is Generated

`starship.toml` is produced by [`starship/gen.py`](./starship/gen.py). Editing it directly works until the next generator run overwrites it, and there is a good reason for the indirection.

**Nerd Font icons live in the Private Use Area, and they do not survive ordinary text editing reliably.** While building this config, every glyph in the range `U+E000`–`U+F8FF` — Apple, Docker, git branch, Node, Python — was silently stripped to an empty string on write. Characters from the supplementary plane (`U+F10FE` Kubernetes, `U+F1062` Terraform) survived. Nothing looked broken in the file; the icons were simply gone, visible only in a hex dump.

The generator sidesteps this by never typing a glyph. It reads the font's own tables and resolves icons **by name**:

```python
mac      = g('md-apple')          # -> U+F0035
proxmox  = g('dev-proxmox')       # -> U+E937
branch   = g('md-source_branch')  # -> U+F062C
```

[`fontmap.py`](./starship/fontmap.py) parses the TTF `cmap` and `post` tables and returns a glyph-name → code-point mapping. It also finds the font on disk rather than assuming a path, so the generator runs on Linux too.

### The icon that was almost wrong

Web sources widely give `U+F0FF` as the Proxmox logo. Looking it up in the actual font, `U+F0FF` is `fa-bimobject` — a completely unrelated symbol that happens to exist at that code point. The Proxmox glyph is `U+E937`, `dev-proxmox`.

This is the argument for resolving by name in one sentence: a code point that renders *something* gives no signal that it is the wrong something.

### Icon size

All icons use the Material Design (`md-`) set where one exists. Those glyphs are drawn on a larger em box than the `fa-` and `dev-` equivalents and read noticeably bigger at the same font size. `dev-proxmox` is the exception — there is no Material variant.

The bigger lever is the terminal font: **`JetBrainsMono Nerd Font`, not the `Mono` variant.** See [README](./README.md#warp-as-the-terminal).

## Colour: The Rule That Prevents The Obvious Mistake

The first colour scheme was neon turquoise and pink. It was unreadable, and the reason is measurable rather than a matter of taste: the purple segment came out at **3.2:1** contrast against its text. The WCAG minimum for body text is 4.5:1.

So the generator does not accept text colours at all. A palette declares **four background colours**, an accent and a line colour. Everything else is computed:

- **Text colour per segment** — dark ink or light ink, whichever wins the contrast comparison against that specific background.
- **The ✔ and ✘ colours** — the most saturated green and red that still clear 5:1 against the right-hand segment. On a light segment that means a dark green, not a neon one.
- **The empty-tab colours** — a shade of the neighbouring segment at roughly 2:1, enough to see the step without shouting.
- **The clock segment** — a sibling shade of the right-hand segment, chosen in whichever direction keeps its own text legible.

Every run prints the worst contrast in the palette. If a scheme drops below 5:1, you see it before you install it.

That guard has already caught two real problems: Gruvbox's right-hand segment sits at a mid lightness where neither a dark nor a light green reaches 5:1, so the segment itself gets darkened until the accents fit; and when the clock got its own segment, Gruvbox fell to 4.4:1 until the sibling-shade function learned to pick the other direction.

## The Status Icon

The ✔ and ✘ do **not** come from Starship's `status` module. That module can show both symbols, but it has a single `style` option — the checkmark and the cross would have to be the same colour, which defeats the point.

They come from the `character` module instead, moved out of the input line and into the right-hand segment. Its `success_symbol` and `error_symbol` each carry their own full style, so the check is green and the cross is red. The `❯` on the input line is then plain static text.

A custom module cannot do this: Starship does not pass the exit code to them. That was verified by dumping the environment from inside one — only `STARSHIP_CONFIG` is there.

## Spacing And Timing

Two knobs at the top of `gen.py`:

```python
SPACE_ABOVE    = 1   # blank lines above the bar (separates blocks)
SPACE_IN_BLOCK = 1   # blank lines between the bar and the ❯
```

`cmd_duration` has `min_time = 0`, so every command reports its runtime, and `show_milliseconds = false`, which prints `1s` and `45s` rather than `1s234ms`. Anything under a second shows `0s`.

The whole prompt renders in **18–30 ms**. The slowest modules are `directory` and `git_status` at roughly 11 ms each, and they run in parallel — the floor is Starship's own process start.

## Rolling It Out

The same `starship.toml` runs everywhere. From the dev machine:

```bash
./servers/deploy.sh root@pve0 root@node0 root@node1 root@node2
```

Or on a single host, without a clone:

```bash
curl -fsSL https://raw.githubusercontent.com/feyzekrn/Homelab/main/setup/devpc/servers/bootstrap.sh | bash
```

Details, and what deliberately does not get installed on a server, in [servers](./servers).

## Changing Something

```bash
cd setup/devpc/starship
$EDITOR gen.py          # palette, spacing, icons
python3 gen.py          # regenerate starship.toml
cp starship.toml ~/.config/starship.toml
```

Do not edit `starship.toml` by hand — the next generator run discards it, and the Private Use Area problem above is waiting. A warning to that effect sits in the file header.
